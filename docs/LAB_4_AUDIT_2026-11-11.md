## Goluri confirmate in codul comun actual

1. **Subscriber queues nu sunt implementate.** `Broker.request_dispatch` este inca
   `self.delivery.call`; Gateway apeleaza `MessageBroker.Call` direct. Exista cozi de topics,
   dar ele nu inlocuiesc cozile request/reply cerute de G6 si issue #264.
2. **Circuit breaker-ul este inca `NoCircuitBreaker`.** Filtrarea instantelor a fost adaugata,
   dar nu exista starea reala a circuitelor. `GrpcDelivery.call` alege o singura instanta si
   intoarce 503 la eroare; nu reia acelasi request pe alta instanta. G10 HA nu este demonstrat.
   Retry-ul operatiilor mutante necesita si idempotenta, conform contractului existent.
3. **Load-aware routing este incomplet conectat.** Exista `update_load`, dar nicio utilizare
   in codul de productie nu actualizeaza cache-ul. Fara worker/SD integration, toate instantele
   au load implicit NORMAL si selectorul ruleaza practic round-robin.
4. **Durable queues si DLC lipsesc din aplicatia comuna.** Store-ul folosit este
   `MemoryTopicStore`, iar `on_rejected` ramane None. Nu exista endpoint de listare DLC.
5. **Compose-ul comun este inca Lab 3.** Lipseste serviciul `message-broker`; serviciile
   folosesc imagini 0.4.x si mod Http. Lipsesc activarea Messaging/Grpc si BROKER_GRPC_URL.
   Pointerele Applicant/Credential/Broker/SD/Gateway sunt inca la release-urile main vechi.
6. **Grafana nu acopera inca toate serviciile.** Panourile request rate/errors/P95/threads
   interogheaza numai metricile Spring rules/record. Pentru Applicant/Credential exista doar
   seria generica `up`; lipsesc panourile bazate pe `service_requests_total`,
   `service_errors_total`, `service_request_duration_seconds_sum`, `service_active_requests`.
   Nu exista scrape pentru player/session/moderation/dms/gateway/SD in aceasta configuratie.

## Probleme concrete in Gateway

- `main.py` trimite `request.url.path`, fara query string. Proba locala cu broker stub a trimis
  `GET /applicants?sessionId=...`, dar brokerul a primit doar `/applicants`. Aceeasi problema
  afecteaza filtrarea `/credentials?applicantId=...`. Aceasta este o proba a maparii Gateway,
  nu un test E2E cu serviciile reale.
- `requirements.txt` fixeaza `grpcio==1.65.1`, dar codul generat impune `grpcio>=1.78.0`.
  Codul generat foloseste si protobuf runtime >=6.31.1, care nu este declarat in requirements.
  Este necesara alinierea dependentelor pentru o instalare curata.
- Testele rutelor sunt ramase la comportamentul vechi: 36 passed, 4 failed. Cele patru erori
  cer ca rutele internal eliminate sa fie inca rutate. Corectia este actualizarea testelor
  pentru 404, pastrand eliminarea rutelor.
- PR #22 nu afiseaza checks; ultimul run pentru dev, la commitul a2143493, este
  [startup_failure](https://github.com/diana7376/gateway-service/actions/runs/42856158454).
  Cauza exacta a erorii Actions nu a fost stabilita din aceasta stare.
- Workflow-ul si versiunea Gateway sunt inca 0.4.1; trebuie pregatit un tag nou pentru Lab 4.

## Ce mai are de facut Mihai

In ordinea recomandata:

1. **Corectie in Applicant si Credential:** `Messaging/ServiceRpc.cs` construieste reply-ul
   cu X-Request-Id, X-Instance-Id si eventual Location, dar nu copiaza Content-Type de la
   rezultatul JSON. Gateway retransmite doar headerele din ServiceReply. Transmite Content-Type
   si verifica raspunsul HTTP final prin Gateway, inclusiv body/status/headere si query filters.
   Fisierele inspectate local au exact acelasi Git blob SHA ca dev-ul live al celor doua servicii.
2. **Integrare cu Diana:** repararea query string in Gateway si alinierea dependentelor sunt
   in partea ei. Verificati impreuna filtrarea listelor si lantul real
   Gateway -> Broker -> Applicant -> Credential -> University Record. Testele din 9 noiembrie
   au folosit explicit un fixture University Record; aceasta limita nu a disparut prin merge.
3. **Monitoring:** ofera Dianei metricile tale documentate in monitoring/README.md si confirma
   ca panourile Applicant/Credential arata request rate, errors, durata medie si active requests.
   Metricile actuale nu includ histogram buckets, deci nu demonstreaza P95 pentru serviciile tale.
4. **Release-urile proprii:** dupa corectie si validare, finalizeaza
   [Applicant #12](https://github.com/caramisca/applicant-service/pull/12) si
   [Credential #13](https://github.com/caramisca/credential-service/pull/13), ambele acum
   draft, MERGEABLE/CLEAN si cu CI verde. Review-ul contractului comun nu mai este blocaj.
   Release-urile personale nu necesita preluarea implementarii breaker/DLC de la colegi.
5. **Dupa publicare:** verifica imaginile publice 0.5.0 pentru amd64/arm64 si ca latest are
   acelasi digest. Apoi pregateste partea ta din PR-ul CPR: gitlink-uri la commiturile finale
   main, imagini 0.5.0 si configuratia Messaging/Grpc, coordonat cu integrarea Dariei (#243).
6. **Predare:** actualizeaza raportul livrarii si dovezile cu starea reala dupa integrare;
   demonstreaza generare/citire, topic cleanup, duplicate, restart si recuperare cu componentele
   reale. Persistenta brokerului poate fi demonstrata doar dupa integrarea store-ului lui Andi.

La verificarea publica DockerHub, tagurile 0.5.0 pentru Applicant, Credential si Message Broker
au raspuns fiecare HTTP 404. Nu sunt tratate drept release-uri publicate.
